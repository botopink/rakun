# Decision 697 — A type's or a behavior's methods' decorators run before the owner's; a method's `compiler.setMeta` / `addMeta` is kept for its owner (one value per type and method, `decorator-meta-twice`), and the owner's body reads it through `compiler.methods(decl)` — `compiler.meta<Query>(m)` / `compiler.metaAll<Query>(m)` (576 (8), 313, 298).

`UserRepository` carries `#[repository]`, and two of its methods carry their own decorators: `#[query("…")]` keeps one `Query` per method with `compiler.setMeta`, and `#[tag("…")]` keeps a `Tag` with `compiler.addMeta`, which may repeat (`count` has two). The methods' decorators run first, so when `repository` runs over the type, `compiler.methods(decl)` hands it every method and `compiler.meta<Query>(m)` / `compiler.metaAll<Tag>(m)` read what each one kept; `describe`, which has no decorator, answers `null` and is skipped. The owner turns that into one line and prints it from its `compiler.init` executor, before `main`: `UserRepository | findById: SELECT id, name FROM users WHERE id = :id [users] | count: SELECT count(*) FROM users [users,count]`, then `main` prints `user 7`. A second `#[query]` on one method would set the same meta type twice and is `decorator-meta-twice`; a decorator on a field keeps no meta, and a string meta on a method stays refused. rakun-data's `#[query]` is such a method decorator; its owner reading the statements this way is front 150's.

Cells in this repository that prove it: none yet; the repositories that read their methods' meta come with front 150 (rakun-data's `#[query]`, decision 313).
